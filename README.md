# SDXL на RTX 2080 Ti: анализ вычислительных затрат и гипотезы ускорения

Домашнее задание №1. Модель: **Stable Diffusion XL 1.0 (base)**, область: Computer Vision (генерация изображений).
Целевая платформа: **NVIDIA GeForce RTX 2080 Ti** (Turing, 11 ГБ).

Структура репозитория:

| Файл | Что в нём |
|---|---|
| `README.md` | отчёт: описание модели, затраты, ограничения, bottleneck'и, методы ускорения, компромиссы |
| `analysis/analyze.py` | подсчёт параметров и FLOPs по компонентам и блокам (на meta-устройстве, веса не нужны) |
| `analysis/analysis.json` | результаты подсчёта |
| `benchmark/benchmark.py` | замеры латентности и пиковой памяти на карте для проверки гипотез |
| `requirements.txt` | зависимости |

Все цифры FLOPs ниже получены `analysis/analyze.py` через `torch.utils.flop_counter` (1 MAC = 2 FLOP). Оценки времени аналитические, их нужно подтвердить `benchmark.py`.

## 1. Описание модели

SDXL — латентная диффузионная модель (Podell et al., 2023). Изображение генерируется не в пикселях, а в латентном пространстве VAE, в 8 раз меньшем по каждой стороне: картинке 1024×1024 соответствует латент 128×128×4.

Пайплайн инференса:

1. **Два текстовых энкодера** (CLIP ViT-L и OpenCLIP ViT-bigG) превращают промпт в 77 токенов размерности 2048 и пулинг-вектор. Вызываются один раз.
2. **UNet** предсказывает шум. Вызывается на каждом шаге сэмплера (обычно 30–50), и при classifier-free guidance — дважды за шаг (условный и безусловный проход, на практике батч 2).
3. **VAE-декодер** переводит итоговый латент в картинку 1024×1024. Вызывается один раз.

| Компонент | Параметры | Веса fp16 |
|---|---:|---:|
| UNet | 2 567 М | 5,13 ГБ |
| Текстовый энкодер 1 (CLIP ViT-L) | 123 М | 0,25 ГБ |
| Текстовый энкодер 2 (OpenCLIP ViT-bigG) | 695 М | 1,39 ГБ |
| VAE (декодер 49 М) | 84 М | 0,17 ГБ |
| **Итого** | **3 469 М** | **6,94 ГБ** (fp32: 13,9 ГБ) |

### Архитектура UNet

Три уровня разрешения латента; трансформерные блоки (self-attention → cross-attention к тексту → FFN с GEGLU) распределены неравномерно:

| Уровень | Каналы | Трансформерных блоков на слой | Токенов (1024×1024) |
|---|---:|---:|---:|
| 128×128 | 320 | 0 (только ResNet-блоки) | — |
| 64×64 | 640 | 2 | 4 096 |
| 32×32 | 1280 | 10 | 1 024 |

В отличие от SD 1.5, на самом высоком разрешении внимания нет вовсе, а основная масса параметров сосредоточена в глубоком стеке из 10 трансформерных блоков на уровне 32×32.

## 2. Источники вычислительных затрат

### Весь пайплайн (1024×1024, 30 шагов, CFG)

| Этап | FLOPs | Доля |
|---|---:|---:|
| UNet: 30 шагов × 2 прохода × 6,76 TFLOP | 405,7 TFLOP | **97,5 %** |
| VAE-декодер | 10,5 TFLOP | 2,5 % |
| Текстовые энкодеры | 0,1 TFLOP | <0,1 % |

Вывод: время определяется числом вызовов UNet. Один вызов VAE-декодера дороже одного вызова UNet (10,5 против 6,8 TFLOP), но он делается один раз.

### Один вызов UNet по типам операций (1024×1024)

| Операция | Что это | Доля FLOPs |
|---|---|---:|
| `addmm` + `mm` | линейные слои трансформеров: Q/K/V/out-проекции, FFN (GEGLU), cross-attention | **64 %** |
| `convolution` | ResNet-блоки, down/upsample | 24 % |
| `bmm` | ядро внимания: QKᵀ и softmax·V | 12 % |

### Один вызов UNet по блокам (1024×1024)

| Блок | Доля |
|---|---:|
| down_blocks.0 (128×128) | 1,9 % |
| down_blocks.1 (64×64) | 8,1 % |
| down_blocks.2 (32×32) | 21,6 % |
| mid_block (32×32) | 11,8 % |
| up_blocks.0 (32×32) | **35,9 %** |
| up_blocks.1 (64×64) | 15,9 % |
| up_blocks.2 (128×128) | 4,8 % |

**69 % вычислений приходится на уровень 32×32**, то есть на глубокие трансформерные стеки с 1280 каналами. Это важно для выбора методов ускорения (см. раздел 5).

### Зависимость от разрешения

| Разрешение | UNet, TFLOP | из них ядро внимания |
|---|---:|---:|
| 512×512 | 1,59 | 0,06 (3,5 %) |
| 768×768 | 3,64 | 0,26 (7,0 %) |
| 1024×1024 | 6,76 | 0,78 (11,6 %) |

Линейные слои и свёртки растут пропорционально площади, а ядро внимания — квадратично от числа токенов: при переходе 512 → 1024 общие FLOPs растут в 4,3 раза, а внимание в 14 раз.

## 3. Целевая платформа и ограничения

| Характеристика RTX 2080 Ti | Значение |
|---|---|
| Архитектура / compute capability | Turing / sm_75 |
| Видеопамять | 11 ГБ GDDR6 |
| Пропускная способность памяти | 616 ГБ/с |
| FP32 | ≈13,4 TFLOPS |
| FP16 на тензорных ядрах (накопление в FP32, GeForce) | ≈54 TFLOPS |
| bf16 | нет аппаратной поддержки |
| FlashAttention-2 / SDPA flash-backend | не поддерживаются (нужен Ampere, sm_80+) |

### Память
- **fp32 невозможен:** веса занимают 13,9 ГБ при 11 ГБ памяти. Работать можно только в fp16.
- **fp16 без запаса:** 6,9 ГБ весов плюс активации, workspace cuDNN/cuBLAS и CUDA-контекст. Пик приходится на VAE-декодер (раздел 4).

### Пропускная способность
- Точка перегиба roofline: 54 TFLOPS / 616 ГБ/с ≈ **88 FLOP/байт**. Большие GEMM UNet (1280 каналов, 1024+ токенов) выше неё и упираются в вычисления.
- GroupNorm, LayerNorm, GELU/GEGLU, softmax, сложения residual имеют интенсивность единицы FLOP/байт и упираются в память. По FLOPs их почти не видно, но по времени они могут занимать заметную долю — это гипотеза для проверки профилировщиком.

### Железо и софт
- Нет bf16, поэтому всё в fp16, а у fp16 узкий динамический диапазон: стандартный VAE SDXL в fp16 переполняется и даёт NaN (чёрные картинки). Нужен VAE в fp32 или специально дообученный fp16-совместимый VAE.
- Нет FlashAttention-2: доступен только memory-efficient backend SDPA (или xFormers), который экономит память, но медленнее flash на новых картах.
- Turing поддерживает CUDA 12 и TensorRT, так что компиляция графа возможна.

### Оценка времени (аналитическая)
Один шаг (батч 2): 13,5 TFLOP. При пиковых 54 TFLOPS это 0,25 с, при реалистичной утилизации 40 % — около 0,6 с. 30 шагов дают порядка **15–20 с на картинку 1024×1024**. Подтвердить замером: `python benchmark/benchmark.py --config baseline`.

## 4. Проблемные места (bottleneck'и)

1. **Итеративность сэмплинга.** 30–50 шагов × 2 прохода CFG = 60–100 последовательных вызовов UNet. Главный множитель времени: 97,5 % FLOPs.
2. **Глубокие трансформерные стеки на 32×32.** 69 % FLOPs одного вызова UNet; основную часть дают линейные слои (QKV, FFN), а не квадратичное внимание.
3. **Внимание на 64×64 (4 096 токенов).** Матрица внимания одного слоя при батче 2 и 10 головах — 671 МБ в fp16 без memory-efficient ядра. Без FlashAttention-2 этот блок упирается в память и растёт квадратично с разрешением.
4. **VAE-декодер.** 10,5 TFLOP за вызов и пиковая память: тензор 128 каналов на 1024×1024 занимает 268 МБ, а матрица self-attention в mid-блоке на 16 384 токенах — 537 МБ в fp16. Плюс переполнение fp16 (NaN).
5. **Объём весов.** 6,9 ГБ из 11 ГБ уходят на веса, остаток ограничивает батч и разрешение.
6. **Memory-bound поэлементные операции** (нормализации, активации, residual), которые не попадают в FLOPs, но тратят пропускную способность.

## 5. Возможные методы ускорения (гипотезы)

Гипотезы сгруппированы по bottleneck'ам. Ожидаемый эффект — оценка, которую проверяет `benchmark.py`.

| # | Метод | Бьёт по | Ожидаемый эффект | Конфиг в `benchmark.py` |
|---|---|---|---|---|
| H1 | Быстрые сэмплеры (DPM-Solver++) с 15–20 шагами вместо 30–50 | 1 | время ∝ числу шагов: ×1,5–2,5 | `dpm20` |
| H2 | Дистилляция по шагам: LCM-LoRA (4–8 шагов) или SDXL-Turbo (1–4 шага) | 1 | ×4–10 | `lcm4` |
| H3 | Отключение CFG (guidance=1) в дистиллированных моделях | 1 | ×2 (батч 1 вместо 2) | входит в `lcm4` |
| H4 | DeepCache: переиспользовать выходы глубоких блоков между соседними шагами | 2 | на SDXL особенно выгодно, т. к. 69 % FLOPs в глубоких блоках | `deepcache` |
| H5 | SDPA memory-efficient / xFormers вместо наивного внимания | 3 | снимает квадратичную память внимания, умеренный выигрыш по времени | `baseline` использует SDPA |
| H6 | Token Merging (ToMe) на уровне 64×64 | 3 | ограниченный: внимание — лишь 12 % FLOPs, а ToMe экономит в основном на нём | `tome` (опционально) |
| H7 | Tiled / sliced VAE decode + fp16-fix VAE | 4 | снижает пик памяти, убирает NaN; время ≈ то же | `baseline` (fp16-fix VAE), `vae_tiling` |
| H8 | Снижение разрешения генерации (768) + апскейл | 2, 3, 4 | ×1,9 по FLOPs UNet | `res768` |
| H9 | `torch.compile` / TensorRT: слияние поэлементных операций и выбор ядер | 6 | 10–30 % на memory-bound частях | `compile` |
| H10 | Квантизация весов UNet в int8 (тензорные ядра Turing поддерживают int8) | 5, 2 | освобождает память; ускорение зависит от наличия int8-ядер в стеке | вне скрипта: TensorRT INT8 |
| H11 | `channels_last` для свёрток | 2 | несколько процентов на свёрточной части (24 %) | `compile` |
| H12 | CPU offload текстовых энкодеров (выгрузка после кодирования промпта) | 5 | −1,6 ГБ памяти, почти без потерь времени | `offload` |

**Главная гипотеза отчёта:** на SDXL выигрывают методы, уменьшающие **число вызовов UNet** (H1–H4), а не методы, оптимизирующие внимание (H5–H6), потому что основная стоимость сидит в линейных слоях глубоких блоков, а не в квадратичном внимании.

## 6. Ожидаемые инженерные компромиссы

| Метод | Выигрыш | Цена |
|---|---|---|
| Меньше шагов (H1) | время | хуже мелкие детали; ниже FID на малом числе шагов |
| Дистилляция LCM/Turbo (H2, H3) | время ×4–10 | ниже разнообразие и следование промпту; Turbo нативно 512×512; без CFG нельзя усилить guidance |
| DeepCache (H4) | время | накопление ошибки при большом интервале кэширования; доп. память под кэш |
| ToMe (H6) | время, память внимания | артефакты при высоком коэффициенте слияния; небольшой выигрыш на SDXL |
| Tiled VAE (H7) | память | возможны швы на стыках тайлов; немного медленнее |
| fp16-fix VAE (H7) | убирает NaN без fp32 | небольшие отличия выходов от оригинального VAE |
| Низкое разрешение + апскейл (H8) | время, память | теряется детализация, апскейлер сам стоит времени |
| `torch.compile` / TensorRT (H9) | время | долгая компиляция, фиксированные формы входа, сложнее отладка |
| int8 (H10) | память | калибровка, риск артефактов; на Turing мало готовых путей для диффузии |
| CPU offload (H12) | память | задержка на перенос весов при смене промпта |

Качество для компромиссов измеряется на фиксированном наборе промптов и сидов: **CLIP-score** (соответствие промпту), **FID** против baseline-генераций (на ≥1–2 тыс. картинок, иначе FID нестабилен) и **LPIPS** до baseline-картинки с тем же сидом (насколько изменилась картинка).
